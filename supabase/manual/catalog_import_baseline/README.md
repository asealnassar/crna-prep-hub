# Production-applied catalog baseline — DO NOT REGENERATE, DO NOT RERUN

This directory holds the catalog import package **as it was applied to
production**, frozen. Nothing in here is generated by a build; nothing in here
may be overwritten by one.

It exists because the generated package one directory up is no longer the thing
production ran.

## What happened

The 63-set / 80-document catalog was imported into production from the package
in this directory. Afterwards, the verified typography was normalized out of
`other_instructions` and into the structured `font_family`, `font_size_pt` and
`margins_inches` columns — 14 documents changed — and
`scripts/build_statement_requirements_import_sql.py` was re-run. That
regeneration **overwrote** `supabase/manual/statement_requirements_catalog_import.sql`
and its preflight, postcheck and manifest in place.

So the files one directory up now describe the DESIRED state. Production holds
the state described here. The two differ by exactly the 14 rows.

## These files are a faithful reproduction, not the original bytes

The original package was never committed — it was generated on a branch and the
regeneration overwrote it, so git has no copy to restore. **That is the gap this
directory closes, and it is why these files must be committed.**

They were reproduced by restoring the pre-normalization
`12_statement_requirements_preview.csv` (kept here as
`12_statement_requirements_preview.baseline.csv`) and re-running the same build
script, which is deterministic: same inputs, same bytes. The reproduction is
confirmed by the fingerprint the package records for its own input —
`10ba99d9c8c9c067dcba88677c4d83f88741c7fda7f08504aa6654cb7c8ac9e4` — which is
the value read from the research directory *before any file was edited*.

## The import must never be rerun — but not because it would overwrite

**Neither package can overwrite anything, and it is worth being exact about
why**, because the wrong reason leads to the wrong fix.

Both files are one transaction. They stage the payload into TEMP tables
(`_import_sets`, `_import_docs`, `_held_back`) and then run a precondition
block which, among other checks, requires the catalog to be **empty**:

```
-- 5 + 6. the catalog must be EMPTY. Not "mostly empty".
select count(*) into v_n from public.statement_requirement_sets;
if v_n <> 0 then
  v_fail := array_append(v_fail, format('statement_requirement_sets already holds %s row(s). This import is for an empty catalog; it does not merge. ...', v_n));
```

A failure raises `IMPORT REFUSED … NOTHING WAS INSERTED`, which aborts the
transaction. That block sits **before** either of the two statements that write
to `public` (the raise is ~10 lines above the first `insert into public.`), and
there is **no `ON CONFLICT`, `DELETE`, `TRUNCATE` or `UPDATE` anywhere in either
file** — the only `on conflict` in the text is a comment explaining its absence,
and every `truncate` match is the enforcement value `'truncated'`.

So a literal rerun against the current catalog finds 63 sets and 80 documents,
refuses, inserts nothing, and rolls back. **Production is unchanged.**

### Then why the rule?

Two reasons, neither of which is "it would overwrite":

1. **It cannot deliver the correction.** The import has no update path at all.
   Running it can only ever refuse.
2. **The refusal invites a destructive fix.** An operator facing
   `IMPORT REFUSED … already holds 63 row(s)` is one step from emptying the
   tables first or adding an upsert so it "works" — and *that* would discard
   activation state, admin catalog edits and promoted submissions.

The 14-row correction is a **targeted UPDATE against those ids**, with its own
preflight asserting each row still holds its expected pre-correction values, so
it cannot run twice or against drifted data. It has not been written.

`statement_requirements_catalog.baseline.json` is the local review payload as it
stood at import, kept for the same reason: it is what the production rows say.
